Hash join and SIP

Analytic databases often join a large table with a small one using a hash join. Vertica adds an optimization called SIP that removes rows with no possible match before they reach the join. This page starts with how to read a query plan, then shows the order in which a hash join finds matches, how SIP passes a filter sideways, and where the filter cannot be used.

The description of SIP follows the design that Vertica engineers described in two papers from 2012 and 2013. Current versions of Vertica may behave differently.

1The plan at a glance

When a database receives a query, it first makes a query plan. A plan is a tree of operators. The scan operators at the bottom read rows from tables and hand them up; each operator above takes those rows, works on them, and hands its own output further up. The second line in each box of the model is the number of rows that operator read or handed on.

The example on this page joins an orders table with a table of VIP customers on the customer number. Orders is the large table and VIP customers is the small one. A join operator has two inputs. The side it reads first is called the inner input, and the side it reads afterwards while looking for matches is called the outer input. The optimizer normally makes the smaller input the inner one.

In a plan without a filter, the outer scan reads all 6 order rows and hands them all to the join. The join takes all 6 and outputs only the 2 that have a match.

SELECT o.*
FROM orders o                 -- large table: outer
JOIN vip_customers v          -- small table: inner
  ON o.customer_id = v.customer_id;
  1. The inner scan reads the 2 VIP customer rows and hands them to the join.
  2. The outer scan reads all 6 order rows and hands them to the join.
  3. The join outputs only the 2 rows that have a match.

A plan is a tree of operators that hand rows upward, and without a filter the join receives every outer row.

2Hash join: build first, then probe

A hash join works in two phases. First it reads the whole inner input and builds a hash table from it (build). Then it reads the outer rows one by one and looks up the same key in the hash table (probe). A hash table is a lookup table that puts each key into a slot, called a bucket, chosen by passing the key through a hash function. The same key always lands in the same bucket, so a lookup only needs to check one bucket.

In this model the hash value is the key modulo 4. The inner keys 17 and 42 go into buckets 1 and 2. The outer row 8 looks in bucket 0, finds it empty, and has no match; 17 finds the same key in bucket 1 and becomes a match.

There is waste in this. Every outer row is read and carried to the join whether it has a match or not, and only then thrown away. Only 2 of the 6 outer rows have a match, yet the join receives all 6.

key mod 4 (bucket)
inner:  17 → 1   42 → 2
outer:   8 → 0   17 → 1   23 → 3
        31 → 3   42 → 2   56 → 0
  1. Read the inner keys and build the hash table.
  2. Read the 6 outer rows and send them all to the join.
  3. For each row the join looks in its bucket and keeps only the rows with a match.

A hash join builds a lookup table from the inner input and checks every outer row against it.

3SIP: passing the filter sideways

SIP (sideways information passing) reduces the waste from chapter 2. After building its hash table, the join passes the key information to the outer scan, and the scan uses it as a filter. The information travels against the order of execution, sideways from the join to the scan, which is where the name comes from.

According to the 2013 paper, Vertica reuses the join's hash table itself as the filter. It also builds a separate set of keys (a hash set) for each join key. These sets are filled while the hash table is being built, and they also record the smallest and largest key. The scan checks each row against the filter as soon as it reads it, and a row whose key is not there is dropped on the spot instead of being sent to the join.

The smallest and largest key also work at a larger scale than single rows. Tables are stored in blocks, and if every key in a block lies outside the range [17, 42], the scan skips that block without reading it. A block with keys from 50 to 90, for example, never needs to be opened.

SIP filter (filled while the hash table is built)
  key set    {17, 42}
  smallest   17
  largest    42
scan:   8 ✕   17 ✓   23 ✕   31 ✕   42 ✓   56 ✕
  1. Build the hash table from the inner keys.
  2. Make a filter from the hash table's keys and put it in front of the outer scan.
  3. Outer rows pass the filter first, and rows without a match are dropped right there.
  4. The join receives only the 2 rows with a match.

SIP passes the join's key information to the scan, so rows without a match are dropped as they are read.

4Same query, filter off and on

Putting the same query side by side, once without a filter and once with the SIP filter on, makes the difference clear. The same 6 order rows go into both sides.

Without the filter, the join receives 6 rows and throws away 4 of them. With the filter, the scan removes those 4 rows first and the join receives only 2. Both sides return the same 2 rows. The filter drops only rows that have no match, so the result does not change; only the number of rows carried to the join does.

The smaller the share of outer rows that have a match, the more the filter saves. If almost every row finds a match, the filter has nothing to remove and only adds checks. The 2013 paper describes the engine switching off such filters by itself while the query runs.

SIP does not change the result; it moves the place where unmatched rows are dropped from the join to the scan.

5Where the filter cannot cross

Vertica stores a table's rows spread over several nodes (servers). This is called segmentation, and a fixed expression, such as a hash of the key, decides which node each row goes to. If two rows that should be joined sit on different nodes, one of them has to be sent at run time to the node that matches its key. This is called resegmentation, and it goes over the network.

In the design described in the 2013 paper, a SIP filter cannot cross such a network step. If the outer input has to be resegmented before the join, the filter cannot be pushed down to the scan. Each node's scan then reads all of its rows and sends them to other nodes, and rows without a match are dropped only at the join, after they have crossed the network.

This is not the only case where the filter is not used. According to the same paper, no filter is used for joins that must keep every outer row (LEFT OUTER JOIN, FULL OUTER JOIN) or for anti-joins (conditions such as NOT IN). A filter that removes almost nothing is switched off by the engine while the query runs, as chapter 4 mentioned.

node 1 scan:  8, 17, 23
node 2 scan: 31, 42, 56
join node: even key → node 1, odd key → node 2
  → 17 and 23 cross to node 2, 42 and 56 cross to node 1
  1. The scans on both nodes each read all 3 of their rows.
  2. Rows cross the network to the node that matches their key.
  3. Rows without a match are dropped only at the join.

In the 2013 design, a network step between the join and the scan keeps the SIP filter from reaching the scan.

Glossary

Query plan
The tree of operators a database builds to run a query. Each operator hands the rows it produces to the operator above.
Scan
The operator that reads rows from a table. It sits at the bottom of the plan.
Join
The operation that pairs rows from two tables that have the same key.
Inner and outer input
The two inputs of a join. The inner input is read first; the outer input is read afterwards while looking for matches. The smaller input is usually the inner one.
Hash table
A lookup table that puts each key into a bucket chosen by a hash function.
Hash join
A join that builds a hash table from the inner input, then looks up each outer row's key in it.
SIP
Sideways information passing. An optimization that passes the join's key information to the outer scan, so rows without a match are dropped at the scan.
Block skipping
Not reading a storage block when all of its keys lie outside the filter's smallest-to-largest range.
Segmentation
Storing a table's rows spread over several nodes according to a fixed expression.
Resegmentation
Sending rows at run time to the node that matches their key, over the network.
Anti-join
A join that keeps only the rows that have no match. Conditions such as NOT IN run this way.
